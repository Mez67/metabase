# نمونه‌ی اولیه: Metabase متن‌باز در برابر Apache Superset

این پوشه دو نمونه‌ی کامل و قابل اجرا دارد که **یک نیاز مشترک** را با دو ابزار BI پیاده می‌کنند:

1. **ورود با Active Directory (LDAP).**
2. **Embed داشبورد** داخل یک پورتال پایتونی، طوری که هر کاربر فقط داده‌ی شعبه‌ی خودش را ببیند (row-level security).
3. **ساخت گزارش با هوش مصنوعی:** کاربر سؤالش را می‌نویسد و نمودار تحویل می‌گیرد. مدل با Ollama روی سرور خودتان اجرا می‌شود.
4. **Audit log:** ثبت ورود، مشاهده‌ی داشبورد و سؤال‌های هوش مصنوعی.

هیچ‌کدام از کدهای این پوشه از بخش `enterprise/` متابیس استفاده نمی‌کند. همه‌چیز روی نسخه‌ی رایگان (AGPL) متابیس یا Superset (Apache 2.0) ساخته شده است.

## ساختار

```
poc/
├── docker-compose.yml        همه‌ی سرویس‌ها، با دو profile: metabase و superset
├── shared/
│   ├── sample-db/init.sql    دیتابیس نمونه‌ی فروش (PostgreSQL) با ۳ شعبه + RLS
│   ├── ldap/                 دایرکتوری آزمایشی به‌جای Active Directory
│   └── ai-service/           سرویس هوش مصنوعی (FastAPI + Ollama)، مشترک بین دو نمونه
├── portal/                   پورتال پایتونی (FastAPI): ورود، embed، هوش مصنوعی، audit log
├── metabase/setup_metabase.py   راه‌اندازی خودکار متابیس
├── superset/                 image، تنظیمات و راه‌اندازی خودکار Superset
└── screenshots/              تصویر هر دو پورتال
```

پورتال و سرویس هوش مصنوعی برای هر دو نمونه **یکسان** هستند. فقط فایل `portal/app/bi.py` تفاوت دارد، یعنی بخشی که داشبورد را embed می‌کند. این‌طوری مقایسه منصفانه است و هر وقت خواستید می‌توانید ابزار BI را عوض کنید.

## اجرا

پیش‌نیاز: Docker و Docker Compose (نسخه‌ی ۲). حدود ۸ گیگابایت RAM لازم است. برای هوش مصنوعی هم حدود ۵ گیگابایت فضا برای مدل.

```bash
cd poc
docker compose --profile metabase up -d --build       # نمونه‌ی ۱: Metabase
docker compose --profile superset up -d --build       # نمونه‌ی ۲: Superset
```

بار اول چند دقیقه طول می‌کشد، چون image‌ها ساخته می‌شوند، مدل هوش مصنوعی دانلود می‌شود و اسکریپت‌های راه‌اندازی اجرا می‌شوند. وضعیت را با این دستور ببینید:

```bash
docker compose --profile metabase --profile superset ps -a
```

وقتی `metabase-setup` و `superset-setup` با `Exited (0)` تمام شدند، همه‌چیز آماده است.

| آدرس | چیست |
|---|---|
| http://localhost:8081 | پورتال با **Metabase** |
| http://localhost:8082 | پورتال با **Superset** |
| http://localhost:3000 | خود Metabase، برای تحلیلگرها |
| http://localhost:8088 | خود Superset، برای تحلیلگرها |

### کاربرهای آزمایشی

رمز همه‌ی کاربرها `Passw0rd!` است.

| کاربر | شعبه | توضیح |
|---|---|---|
| `ali` | tehran | فقط تهران را می‌بیند |
| `sara` | isfahan | فقط اصفهان را می‌بیند |
| `reza` | shiraz | فقط شیراز را می‌بیند |
| `mina` | همه (`*`) | مدیر: همه‌ی شعبه‌ها و صفحه‌ی Audit log را می‌بیند. با گروه AD به ادمین Metabase و Superset هم تبدیل می‌شود |

## نتیجه‌ی تست‌ها

این‌ها را در محیط آزمایشی اجرا کردم:

| آزمون | Metabase | Superset |
|---|---|---|
| ورود با LDAP به پورتال، رد رمز اشتباه، رد کاربر بدون شعبه | ✅ | ✅ |
| `ali` فقط تهران، `sara` فقط اصفهان، `mina` همه | ✅ | ✅ |
| تلاش برای عوض کردن فیلتر شعبه از سمت مرورگر | ✅ رد شد (400) | ✅ فیلتر داخل guest token است |
| هوش مصنوعی فقط داده‌ی شعبه‌ی کاربر را برمی‌گرداند | ✅ | ✅ |
| هوش مصنوعی: رد `DELETE` و رد تلاش برای دور زدن فیلتر | ✅ | ✅ |
| Audit log فقط برای مدیر باز می‌شود | ✅ | ✅ |
| ورود مستقیم تحلیلگر به خود ابزار با LDAP و نگاشت گروه AD به ادمین | ✅ | ⚠️ تست‌نشده (پایین را ببینید) |

**چیزهایی که در محیط آزمایشی من قابل تست نبودند:**
- **مدل واقعی Ollama:** محیط من به سرور مدل‌های Ollama دسترسی نداشت. به‌جای مدل، یک پاسخ‌دهنده‌ی ساختگی گذاشتم که SQL ثابت برمی‌گرداند. پس مسیر کامل تست شده (ساخت SQL، بررسی امنیتی، اجرا، نمودار)، ولی **کیفیت SQLی که مدل واقعی می‌سازد تست نشده است.**
- **ورود LDAP به خود Superset:** به کتابخانه‌ی `python-ldap` نیاز دارد که باید از مخزن Debian نصب شود و محیط من به آن دسترسی نداشت. فایل `superset/Dockerfile` آن را نصب می‌کند و روی سرور شما باید کار کند. اگر مشکلی پیش آمد، با `SUPERSET_AUTH=db` و `SUPERSET_PROVIDER=db` و `SUPERSET_USER=portal` و `SUPERSET_PASSWORD=portal` روی حساب محلی برگردید.

## مقایسه

| موضوع | Metabase متن‌باز | Apache Superset |
|---|---|---|
| **لایسنس** | AGPL. داخل سازمان بدون محدودیت | Apache 2.0. هیچ محدودیتی ندارد و نسخه‌ی پولی هم ندارد |
| **زبان بک‌اند** | Clojure | **Python** |
| **سادگی برای کاربر غیرفنی** | **خیلی ساده**. ساخت سؤال بدون SQL | پیچیده‌تر. بیشتر مناسب تحلیلگر |
| **RLS در embed** | با فیلتر قفل‌شده در توکن. فقط روی فیلترهایی که برای داشبورد تعریف کرده‌اید | **RLS واقعی روی dataset**، با بند SQL دلخواه در guest token |
| **RLS برای کاربرهای داخل خود ابزار** | ❌ در نسخه‌ی رایگان نیست (enterprise) | ✅ داخلش هست (Row Level Security در تنظیمات) |
| **ورود با AD و نگاشت گروه** | ✅ LDAP پایه به‌علاوه‌ی نگاشت گروه | ✅ LDAP به‌علاوه‌ی نگاشت گروه به نقش |
| **SSO با OIDC یا SAML** | ❌ enterprise | ✅ OIDC/OAuth داخلی (Flask-AppBuilder). SAML با یک افزونه‌ی جانبی |
| **برند روی embed** | «Powered by Metabase» می‌ماند و حذفش مجاز نیست | برندی ندارد |
| **Audit log داخلی** | ❌ enterprise. در این نمونه، پورتال ثبت می‌کند | جدول `logs` داخلی دارد. پورتال هم ثبت می‌کند |
| **سفارشی‌سازی با پایتون** | فقط از بیرون، با API | **از داخل**: افزونه، `superset_config.py` و هر کد پایتون |
| **هوش مصنوعی** | سرویس جدای پایتونی (همین نمونه) | همین سرویس. امکان ادغام داخلی هم دارد |
| **مصرف منابع** | سبک (یک JVM) | سنگین‌تر. برای کارهای سنگین Redis و Celery هم لازم می‌شود |

### جمع‌بندی من

- اگر کاربرهای اصلی‌تان **فقط داشبوردهای آماده را داخل پروژه‌ی خودتان می‌بینند** و تحلیلگرها هم **مورد اعتمادند** (همه‌ی داده را می‌بینند)، **Metabase** کافی است و برای ساخت داشبورد خیلی ساده‌تر است.
- اگر لازم دارید **کاربرهای داخل خود ابزار** هم محدود به شعبه‌ی خودشان باشند، یا SSO با SAML یا OIDC بخواهید، یا بخواهید **با پایتون از داخل** توسعه بدهید، **Superset** انتخاب بهتری است. همه‌ی این‌ها را رایگان دارد.

## نکته‌های امنیتی (قبل از استفاده‌ی واقعی)

این یک نمونه‌ی اولیه است. برای محیط واقعی:

1. **همه‌ی رمزها را عوض کنید.** این‌ها در `docker-compose.yml` با پیش‌فرض `change-me` آمده‌اند: `AI_SERVICE_TOKEN`، `PORTAL_SESSION_SECRET`، `SUPERSET_SECRET_KEY`، `MB_ADMIN_PASSWORD`، `LDAP_READONLY_PASSWORD`. آن‌ها را در یک فایل `.env` بگذارید.
2. **HTTPS:** همه‌ی سرویس‌ها را پشت یک reverse proxy مثل nginx با گواهی قرار دهید. در Superset هم `SESSION_COOKIE_SECURE = True` و Talisman را با `frame-ancestors` محدود به آدرس پورتال روشن کنید.
3. **Active Directory:** این متغیرها را در `docker-compose.yml` و `superset/superset_config.py` عوض کنید:
   - `LDAP_URL`، مثلاً `ldaps://dc1.corp.local:636`
   - `LDAP_BIND_DN`: یک حساب سرویس فقط‌خواندنی، مثلاً `svc-reports@corp.local`
   - `LDAP_BASE_DN`، مثلاً `DC=corp,DC=local`
   - `LDAP_USER_FILTER`: `(sAMAccountName={username})`
   - `LDAP_BRANCH_ATTR`: ویژگی‌ای که شعبه را نگه می‌دارد، مثلاً `department`
   - `LDAP_UID_FIELD=sAMAccountName` برای Superset
   - فیلتر کاربر Metabase: `(&(objectClass=user)(|(sAMAccountName={login})(mail={login})))`
   - DN گروه تحلیلگرها: `LDAP_ANALYST_GROUP`
4. **دیتابیس‌های واقعی:** نقش `bi_reader` باید فقط‌خواندنی باشد. سرویس هوش مصنوعی برای هر شعبه یک نقش جدا دارد (`ai_tehran` و...). این نقش‌ها را در `shared/sample-db/init.sql` ببینید. RLS را خود PostgreSQL اعمال می‌کند، پس حتی SQL بدی که مدل بسازد هم نمی‌تواند داده‌ی شعبه‌ی دیگری را بخواند. برای دیتابیس‌های دیگر مثل SQL Server یا Oracle باید همین الگو را با امکانات خود آن دیتابیس پیاده کرد. SQL Server هم RLS دارد.
5. **Ollama:** پیش‌فرض مدل `qwen2.5-coder:7b` است. اگر GPU دارید، بخش `deploy` سرویس `ollama` را از حالت کامنت خارج کنید. با `OLLAMA_MODEL` می‌توانید مدل دیگری امتحان کنید.

## گام‌های بعدی پیشنهادی

- امتحان سرویس هوش مصنوعی با مدل واقعی و سؤال‌های واقعی خودتان، به فارسی و انگلیسی
- اتصال به یکی از دیتابیس‌های واقعی و یک گروه آزمایشی از AD
- انتخاب نهایی بین دو ابزار، و بعد: ذخیره‌ی گزارش‌های هوش مصنوعی داخل ابزار انتخاب‌شده، به‌علاوه‌ی داشبوردهای بیشتر
